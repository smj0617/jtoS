### 013-01 공통 CSS 파일 static/resource/global.css (커밋 `5a00353`)

**만든 파일**
- `src/main/resources/static/resource/global.css`
- `src/test/java/com/mysite/sbb/global/StaticResourceTests.java`

**들어간 코드**
```css
textarea { width: 100%; }               /* 답변 입력칸을 화면 가로 폭에 꽉 채움 */
input[type=submit] { margin-top: 10px; } /* 답변등록 버튼 위 여백 */
```

**설명**
- `src/main/resources/static` 아래 파일은 컨트롤러를 거치지 않고, 폴더 경로가 그대로 주소가 된다. 이 파일의 주소는 `/resource/global.css`다.
- 강사식으로 정적 파일(CSS, JS, 이미지)은 `static/resource` 폴더에 모은다. 그러면 `/questions` 같은 컨트롤러 주소와 섞이지 않는다. 책은 `static/style.css`를 쓴다.

**검증**
- `StaticResourceTests`에서 `GET /resource/global.css`가 200이고, 응답 내용에 `textarea`가 들어 있는지 확인했다.
- 전체 테스트 14개 통과.

### 013-02 목록·상세 템플릿에 공통 CSS 연결 (커밋 `0627858`)

**바꾼 파일**
- `question_list.html`과 `question_detail.html`의 `<head>`
- `QuestionControllerTests.java`

**들어간 코드**
```html
<link rel="stylesheet" type="text/css" th:href="@{/resource/global.css}">
```

**설명**
- 브라우저는 화면을 열 때 이 주소에서 CSS를 받아 와 적용한다. 그래서 답변 입력칸이 넓어지고, 버튼 위에 여백이 생긴다.
- `th:href="@{...}"`는 앱 기준으로 주소를 만든다. 앱이 하위 경로(예: `/sbb`)에 올라가도 주소가 알맞게 바뀐다.
- 남은 문제: 같은 `<head>` 내용을 두 템플릿에 반복해서 적고 있다. 015 레이아웃에서 한곳으로 모은다.

**검증**
- 목록 HTML에 `href="/resource/global.css"`가 들어 있는지 확인했다.
- 테스트 14개 통과.

**013 요약**
- 정적 파일은 `static` 폴더에서 그대로 제공된다.
- 화면(템플릿)은 그 파일을 `<link>`로 불러와 쓴다.
- 파일을 만드는 일(013-01)과 화면에 연결하는 일(013-02)은 별개다.

## 014 부트스트랩

### 014-01 부트스트랩 CSS를 cdnjs CDN으로 연결 (커밋 `ee789ee`)

**바꾼 파일**
- `question_list.html`과 `question_detail.html`의 `<head>`
- `QuestionControllerTests.java`

**들어간 코드**
```html
<link rel="stylesheet" href="https://cdnjs.cloudflare.com/ajax/libs/bootstrap/5.3.3/css/bootstrap.min.css">
<link rel="stylesheet" type="text/css" th:href="@{/resource/global.css}">
```

**설명**
- 부트스트랩은 `table`, `btn`, `card`, `container` 같은 스타일 클래스를 미리 만들어 둔 모음이다. 클래스 이름만 붙이면 모양이 갖춰진다.
- 책은 부트스트랩 파일을 내려받아 `static`에 넣는다. 강사식은 CDN(여러 사이트가 함께 쓰는 공개 파일 서버) 주소를 연결한다. 그래서 프로젝트에 큰 파일을 넣지 않는다.
- 주소에 버전 `5.3.3`을 고정했다. 새 버전이 나와도 화면 모양이 갑자기 바뀌지 않는다.
- 순서가 중요하다. CSS는 나중에 불러온 규칙이 앞의 규칙을 덮어쓴다. 그래서 부트스트랩을 먼저 불러오고 우리 `global.css`를 나중에 불러온다.

**검증**
- 목록 HTML에 부트스트랩 링크가 있는지 확인했다.
- 테스트 14개 통과.

**검증**

### 014-04 상세 화면에 부트스트랩 카드 적용 (커밋 `8c0c357`)

**바꾼 파일**
- `question_detail.html`
- `QuestionControllerTests.java`

**들어간 코드 (요약)**
```html
<div class="container my-3">
    <h2 class="border-bottom py-2" th:text="${question.subject}"></h2>
    <div class="card my-3"><div class="card-body">
        <div class="card-text" style="white-space: pre-line;" th:text="${question.content}"></div>
    </div></div>
    <h5 class="border-bottom my-3 py-2" th:text="|${#lists.size(question.answerList)}개의 답변이 있습니다.|"></h5>
    <div class="card my-3" th:each="answer : ${question.answerList}"> ... answer.content ... </div>
    <form ... class="my-3">
        <textarea name="content" ... class="form-control"></textarea>
        <input type="submit" value="답변등록" class="btn btn-primary my-2">
    </form>
</div>
```

**설명**
- 제목: `border-bottom`은 아래 구분선, `py-2`는 위아래 안쪽 여백이다.
- 질문 내용: `card`(테두리가 있는 상자)에 담았다.
- `white-space: pre-line`은 사용자가 입력한 줄바꿈을 화면에서도 줄바꿈으로 보여 준다. HTML은 이 설정이 없으면 줄바꿈을 무시한다.
- 답변: 012-04의 `<ul><li>` 목록을 바꿔, 답변마다 카드를 하나씩 그린다(`th:each`를 카드 `div`에 붙였다).
- 입력칸 `form-control`은 부트스트랩 입력칸 모양이다. 버튼 `btn btn-primary`는 파란 버튼이다.

**검증**
- 상세 HTML에 `class="card my-3"`와 `class="btn btn-primary my-2"`가 있는지 확인했다.
- 012-04 테스트는 글자만 확인하므로 그대로 통과한다.
- 테스트 14개 통과.

## 015 레이아웃

### 015-01 타임리프 레이아웃 다이얼렉트 의존성 추가

**바꾼 파일**
- `build.gradle.kts`

**들어간 코드**
```kotlin
implementation("nz.net.ultraq.thymeleaf:thymeleaf-layout-dialect")
```

**설명**
- 지금은 목록과 상세 템플릿에 `<head>` 4줄(부트스트랩, 폰트, 공통 CSS, 제목)이 똑같이 반복된다. 화면이 늘어날수록 고칠 곳도 늘어난다.
- 레이아웃 다이얼렉트는 타임리프에 `layout:` 문법을 더해 주는 라이브러리다.
  - 공통 틀 파일 `layout.html`을 하나 만든다.
  - 각 화면은 "나는 이 틀을 쓴다"라고 선언하고, 바뀌는 내용만 적는다.
  - 자바의 상속(부모 틀 + 자식 내용)과 비슷한 방식이다.
- 책 2-15는 `th:replace`로 `<head>` 조각만 가져다 붙인다. 강사식은 틀 전체를 레이아웃으로 쓴다.
- 버전은 적지 않았다. Spring Boot의 의존성 관리가 맞는 버전을 정해 준다.
- 라이브러리가 클래스패스에 있으면 스프링이 자동으로 타임리프에 등록한다.

**검증**
- 의존성만 추가했고, 아직 이 문법을 쓰는 화면은 없다.
- 테스트 14개 통과.

### 015-02 공통 틀 layout.html 추가

**만든 파일**
- `src/main/resources/templates/layout.html`

**들어간 코드 (요약)**
```html
<html xmlns:th="http://www.thymeleaf.org" xmlns:layout="http://www.ultraq.net.nz/thymeleaf/layout">
<head>
    <link ... bootstrap.min.css>
    <link ... pretendard.min.css>
    <link th:href="@{/resource/global.css}">
    <title>SBB</title>
</head>
<body>
<div layout:fragment="content"></div>
</body>
</html>
```

**설명**
- `xmlns:layout`은 이 파일에서 `layout:` 문법을 쓰겠다는 선언이다.
- `<head>`에는 지금까지 화면마다 반복해서 적던 3줄(014-01 부트스트랩, 014-02 폰트, 013-02 공통 CSS)을 옮겨 왔다. 앞으로 CSS나 JS를 더할 때는 이 파일 한 곳만 고치면 된다.
- `<div layout:fragment="content">`는 각 화면의 내용이 들어갈 자리다. 화면 쪽에서 같은 이름(`content`)의 조각을 만들면, 그 조각이 이 자리에 끼워진다.
- `<title>SBB</title>`은 기본 제목이다. 화면별 제목을 붙이는 방법은 015-05에서 다룬다.

**검증**
- 아직 이 틀을 쓰는 화면이 없어서 기존 결과는 그대로다.
- 테스트 14개 통과.

### 015-03 목록 화면이 layout.html 사용

**바꾼 파일**
- `question_list.html`

**들어간 코드**
```html
<html ... xmlns:layout="http://www.ultraq.net.nz/thymeleaf/layout" layout:decorate="~{layout}">
<head>
    <title>질문 목록</title>
</head>
<body>
<div layout:fragment="content" class="container my-3">
    ... 기존 표 그대로 ...
</div>
```

**설명**
- `layout:decorate="~{layout}"`는 "이 화면은 `templates/layout.html` 틀로 감싼다"는 선언이다. `~{layout}`은 템플릿 이름이다.
- `<head>`에서 부트스트랩, 폰트, 공통 CSS 3줄을 지웠다. 이제 틀(`layout.html`)이 그 3줄을 넣어 준다. 화면에는 제목만 남겼다.
- 014-03에서 만든 `container` `div`에 `layout:fragment="content"`를 붙였다. 타임리프는 이 조각을 틀의 `content` 자리에 끼워 최종 HTML을 만든다.
- 결과 HTML은 틀의 `<head>`와 화면의 `<title>`, 그리고 틀의 `<body>` 안에 들어간 화면 내용이 합쳐진 모습이다.

**검증**
- 기존 테스트(013-02 공통 CSS 링크, 014-01 부트스트랩 링크, 014-03 표 클래스)가 고치지 않았는데도 그대로 통과했다.
- 목록 화면에서는 링크를 지웠는데 응답 HTML에는 링크가 있다는 뜻이다. 즉 레이아웃이 실제로 합쳐져 나온다.
- 테스트 14개 통과.

### 015-05 화면 제목 패턴 layout:title-pattern

**바꾼 파일**
- `layout.html`
- `QuestionControllerTests.java`

**들어간 코드**
```html
<title layout:title-pattern="$CONTENT_TITLE | $LAYOUT_TITLE">SBB</title>
```

**설명**
- 레이아웃과 화면에 둘 다 `<title>`이 있을 때, 최종 제목을 어떻게 합칠지 정하는 규칙이다.
  - `$LAYOUT_TITLE`은 틀의 제목(`SBB`)이다.
  - `$CONTENT_TITLE`은 화면의 제목(예: `질문 목록`)이다.
- 결과 제목은 `질문 목록 | SBB`가 된다. 브라우저 탭에서 어느 사이트의 어느 화면인지 바로 알 수 있다.
- 각 화면은 자기 이름만 적으면 된다. 사이트 이름이나 구분 기호를 바꿀 때는 이 한 줄만 고치면 된다.

**검증**
- 목록 응답에 `<title>질문 목록 | SBB</title>`가 들어 있는지 확인했다.
- 테스트 14개 통과.

### 015-06 공통 자바스크립트 global.js

**만든·바꾼 파일**
- `static/resource/global.js`: 새 파일
- `layout.html`
- `StaticResourceTests.java`
- `QuestionControllerTests.java`

**들어간 코드**
```javascript
function onReady(fn) {
    if (document.readyState === "loading") {
        document.addEventListener("DOMContentLoaded", fn);
    } else {
        fn();
    }
}
```
```html
<script defer th:src="@{/resource/global.js}"></script>
```

**설명**
- `global.js`는 `global.css`(013-01)의 자바스크립트판이다. 여러 화면이 함께 쓸 동작을 여기에 모은다.
- `layout.html`에서 한 번만 불러오므로 레이아웃을 쓰는 모든 화면에서 동작한다. 015-04에서 말한 "공통 부분은 레이아웃 한 곳만 고친다"의 첫 예다.
- `defer`를 붙이면 브라우저가 HTML을 끝까지 읽은 뒤 스크립트를 실행한다. 그래서 스크립트 때문에 화면 표시가 늦어지지 않는다.
- `onReady(fn)`은 "화면이 다 준비되면 이 함수를 실행해 줘"라는 도우미다.
  - 아직 읽는 중(`loading`)이면 준비 완료 이벤트(`DOMContentLoaded`)를 기다린다.
  - 이미 준비됐으면 바로 실행한다.
- 이 도우미는 016(첫 오류 칸 focus)과 025(DELETE 링크)에서 쓴다.

**검증**
- `/resource/global.js`가 200이고 `function onReady`가 들어 있는지 확인했다.
- 목록 HTML에 `src="/resource/global.js"`가 있는지 확인했다.
- 테스트 15개 통과.

### 016-05 record 폼 QuestionForm과 서버 검증

**만든·바꾼 파일**
- `build.gradle.kts`
- `domain/question/question/dto/QuestionForm.java`: 새 파일
- `QuestionController.java`
- `QuestionControllerTests.java`

**들어간 코드**
```java
public record QuestionForm(
        @NotBlank(message = "제목은 필수항목입니다.")
        @Size(max = 200, message = "제목은 200자 이하로 입력하세요.")
        String subject,
        @NotBlank(message = "내용은 필수항목입니다.")
        String content
) {}
```
```java
@PostMapping
public String create(@Valid QuestionForm questionForm, BindingResult bindingResult) {
    if (bindingResult.hasErrors()) {
        return "question_form";
    }
    questionService.create(questionForm.subject(), questionForm.content());
    return "redirect:/questions";
}
```

**설명**
- `spring-boot-starter-validation`을 넣어야 `@NotBlank` 같은 검증 어노테이션과 `@Valid`가 동작한다.
- 폼 객체 `QuestionForm`
  - 016-03에서 `@RequestParam`으로 하나씩 받던 입력값을 객체 하나로 묶었다. 입력칸이 늘어나도 메서드 인자가 늘지 않는다.
  - 책은 `@Getter @Setter` 클래스를 쓴다. 강사식은 `record`다. `record`는 필드, 생성자, 접근자(`subject()`)를 자바가 자동으로 만들고, 만든 뒤에는 값을 바꿀 수 없다. 스프링은 폼 값을 생성자로 넣어 record를 만든다.
  - `@NotBlank`는 null, 빈 문자열, 공백만 있는 값을 막는다.
  - `@Size(max = 200)`은 엔티티의 `@Column(length = 200)`과 맞춘 것이다. DB에 저장하기 전에 미리 막는다.
- 컨트롤러
  - `@Valid`가 붙으면 스프링이 객체를 만든 직후 규칙대로 검사한다.
  - `BindingResult`에는 검사 결과(어느 필드가 어떤 메시지로 실패했는지)가 담긴다. 반드시 `@Valid` 객체 바로 뒤에 둬야 한다. 없으면 검증 실패가 400 오류로 끝나 버린다.
  - 오류가 있으면 저장하지 않고 등록 폼을 다시 보여 준다. 화면에 메시지를 표시하는 것은 016-06에서 한다.

**검증**
- 제목에 공백(" ")을 보내면 200 응답과 함께 `question_form` 화면이 다시 나오는지 확인했다.
- 질문 개수가 그대로인지(저장되지 않았는지) 확인했다.
- 016-03의 정상 저장 테스트도 그대로 통과한다(record로 받아도 저장된다).
- 테스트 19개 통과.

### 016-06 th:object·th:field와 필드별 오류 메시지

**바꾼 파일**
- `QuestionController.java`
- `question_form.html`
- `QuestionControllerTests.java`

**들어간 코드**
```java
@GetMapping("/new")
public String showCreate(QuestionForm questionForm) {
    return "question_form";
}
```
```html
<form th:action="@{/questions}" th:object="${questionForm}" method="post">
    <input type="text" th:field="*{subject}" class="form-control" th:errorclass="is-invalid">
    <div class="invalid-feedback" th:if="${#fields.hasErrors('subject')}" th:errors="*{subject}"></div>
    ...
</form>
```

**설명**
- `th:object="${questionForm}"`는 이 폼이 쓸 객체를 정한다. 안쪽의 `*{subject}`는 그 객체의 `subject` 필드를 가리킨다.
- `th:field="*{subject}"`는 입력칸의 `id`, `name`, `value`를 한 번에 채운다. 그래서 016-02에서 손으로 적던 `name`, `id`가 필요 없다.
  - 검증에 실패해 폼이 다시 열리면, 사용자가 입력했던 값이 `value`에 그대로 들어간다. 다시 칠 필요가 없다.
- `th:errorclass="is-invalid"`는 그 필드에 오류가 있을 때만 `is-invalid` 클래스를 더한다. 부트스트랩이 빨간 테두리로 보여 준다.
- `th:errors="*{subject}"`는 그 필드의 오류 메시지(016-05 `QuestionForm`에 적은 `message`)를 출력한다.
  - 부트스트랩의 `invalid-feedback`은 바로 앞 입력칸이 `is-invalid`일 때만 보이는 빨간 글씨다.
  - `th:if`로 오류가 없을 때는 아예 그리지 않는다.
- GET 폼 화면이 `QuestionForm`을 인자로 받는 이유
  - `th:object`는 처음 폼을 열 때도 객체가 필요하다.
  - 인자로 받으면 스프링이 빈 객체(값은 모두 null)를 만들어 모델에 `questionForm`이라는 이름으로 담아 준다.
- 책은 오류를 폼 위에 한꺼번에 보여 준다. 여기서는 칸마다 바로 아래에 보여 준다(강사식).
- `record`인데도 `th:field`가 값을 읽을 수 있는지 걱정했지만, 테스트로 정상 동작을 확인했다.

**검증**
- 제목을 공백으로 보내면 `제목은 필수항목입니다.` 메시지와 `is-invalid`가 나오는지 확인했다.
- 입력했던 내용(`내용`)이 `textarea`에 그대로 남는지 확인했다.
- 테스트 19개 통과.

### 016-07 브라우저 검증 required·maxlength

**바꾼 파일**
- `question_form.html`
- `QuestionControllerTests.java`

**들어간 코드**
```html
<input type="text" th:field="*{subject}" ... required maxlength="200">
<textarea th:field="*{content}" ... required></textarea>
```

**설명**
- `required`는 칸이 비어 있으면 브라우저가 전송 자체를 막고 "이 입력란을 작성하세요" 말풍선을 띄운다.
- `maxlength="200"`은 200자를 넘게 입력할 수 없게 한다.
- 규칙은 016-05 서버 검증(`@NotBlank`, `@Size(max = 200)`)과 같다. 강사식으로 양쪽에서 같은 규칙을 검사한다.
- 두 검증의 역할이 다르다.
  - 브라우저 검증: 서버까지 가지 않고 바로 알려 주는 편의 기능이다. 하지만 개발자 도구로 속성을 지우거나 직접 요청을 보내면 우회된다.
  - 서버 검증: 반드시 통과해야 하는 진짜 방어선이다. 그래서 016-05는 그대로 둔다.
- 참고로 `required`는 공백만 있는 값(" ")은 막지 못한다. 그런 값은 서버의 `@NotBlank`가 잡는다. 016-05 테스트가 바로 그 경우다.

**검증**
- 폼 HTML에 `maxlength="200"`과 `required`가 있는지 확인했다.
- 테스트 19개 통과.

### 016-08 첫 오류 입력칸에 자동 focus

**바꾼 파일**
- `static/resource/global.js`
- `StaticResourceTests.java`

**들어간 코드**
```javascript
onReady(() => {
    const firstInvalid = document.querySelector(".is-invalid");
    if (firstInvalid) {
        firstInvalid.focus();
    }
});
```

**설명**
- 016-06에서 오류가 난 칸에 `is-invalid` 클래스가 붙도록 했다. 이 클래스를 표시로 삼아 오류 칸을 찾는다.
- `document.querySelector(".is-invalid")`는 화면 위에서부터 처음 만나는 요소 하나를 돌려준다. 그래서 첫 번째 오류 칸이 된다.
- `focus()`는 그 칸에 커서를 둔다. 사용자는 마우스로 찾지 않고 바로 고쳐 입력할 수 있다.
- 015-06에서 만든 `onReady`를 써서 화면이 다 준비된 뒤에 실행한다.
- `global.js`는 레이아웃에서 모든 화면에 불러오므로, 앞으로 만들 폼(답변, 회원가입, 수정)에도 따로 코드를 넣지 않아도 똑같이 동작한다.
- 오류가 없는 화면에서는 `querySelector`가 `null`을 돌려주므로 아무 일도 하지 않는다.

**검증**
- MockMvc는 자바스크립트를 실행하지 않는다. 그래서 `global.js` 파일에 해당 코드가 들어 있는지만 확인했다.
- 실제 커서 이동은 브라우저에서 확인할 부분이다.
- 테스트 19개 통과.

### 018-03 주소의 ?page 값으로 페이지 선택 (1부터)

**바꾼 파일**
- `QuestionController.java`
- `question_list.html`
- `QuestionControllerTests.java`

**들어간 코드**
```java
@GetMapping
public String list(@RequestParam(defaultValue = "1") int page, Model model) {
    Page<Question> paging = questionService.getList(Math.max(page, 1) - 1);
    model.addAttribute("paging", paging);
    return "question_list";
}
```
```html
<tr th:each="question : ${paging}">
```

**설명**
- `@RequestParam(defaultValue = "1") int page`는 주소의 `?page=2` 값을 받는다. 값이 없으면(`/questions`) 1이다.
- 사용자에게 보이는 페이지 번호는 1부터 시작한다. 하지만 `PageRequest`는 0부터라서 1을 빼서 넘긴다. 책은 주소에도 0부터 쓰는데(`?page=0`), 사람이 보기에는 1부터가 자연스럽다(강사식).
- `Math.max(page, 1)`은 `?page=0`이나 음수가 들어와도 1페이지로 보게 한다. 그래서 잘못된 주소에도 오류가 나지 않는다.
- 모델 이름을 `questionList`에서 `paging`으로 바꿨다. 이제 목록이 아니라 페이지 정보까지 담은 `Page` 객체이기 때문이다. 템플릿의 `th:each`도 `${paging}`으로 바꿨다.

**검증**
- 테스트 준비에서 저장한 질문(`sbb가 무엇인가요?`)이 가장 오래된 질문이 되도록, 11개를 더 저장했다.
- 최신순 12개 중 12번째라서 `?page=2`에는 보이고, `?page=1`에는 보이지 않는지 확인했다.
- 테스트 21개 통과.

### 018-04 목록 아래 페이지 이동 버튼

**바꾼 파일**
- `question_list.html`
- `QuestionControllerTests.java`

**들어간 코드 (요약)**
```html
<div th:if="${!paging.isEmpty()}">
<ul class="pagination justify-content-center">
    <li class="page-item" th:classappend="${!paging.hasPrevious()} ? 'disabled'">
        <a class="page-link" th:href="@{/questions(page=${paging.number})}">이전</a>
    </li>
    <li th:each="p : ${#numbers.sequence(1, paging.totalPages)}"
        th:if="${p >= paging.number + 1 - 5 and p <= paging.number + 1 + 5}"
        th:classappend="${p == paging.number + 1} ? 'active'" class="page-item">
        <a th:text="${p}" class="page-link" th:href="@{/questions(page=${p})}"></a>
    </li>
    <li class="page-item" th:classappend="${!paging.hasNext()} ? 'disabled'">
        <a class="page-link" th:href="@{/questions(page=${paging.number + 2})}">다음</a>
    </li>
</ul>
</div>
```

**설명**
- `paging.number`는 0부터 시작하는 현재 페이지다. 화면 번호(1부터)로는 `number + 1`이다.
  - 이전 페이지의 화면 번호: `number`
  - 다음 페이지의 화면 번호: `number + 2`
- `@{/questions(page=${p})}`는 `/questions?page=3` 같은 주소를 만든다. 괄호 안이 쿼리 파라미터가 된다.
- `#numbers.sequence(1, paging.totalPages)`는 1부터 전체 페이지 수까지 숫자 목록을 만든다.
  - 페이지가 100개라도 버튼이 100개 나오면 안 된다. 그래서 `th:if`로 현재 페이지 앞뒤 5개만 보이게 했다.
- `th:classappend`는 조건이 참일 때만 클래스를 덧붙인다.
  - `disabled`: 첫 페이지의 "이전", 마지막 페이지의 "다음"을 회색으로 만들고 눌리지 않게 한다.
  - `active`: 현재 페이지 번호를 파란 배경으로 표시한다.
- `th:if="${!paging.isEmpty()}"`가 필요한 이유: 질문이 0개면 전체 페이지가 0이라 `sequence(1, 0)`이 거꾸로 된 목록을 만든다. 그래서 질문이 없으면 버튼 줄을 아예 그리지 않는다.

**검증**
- 질문 12개, 1페이지에서 다음을 확인했다.
  - `href="/questions?page=2"` 링크가 있다.
  - 현재 페이지에 `page-item active`가 있다.
  - 이전 버튼에 `page-item disabled`가 있다.
- 테스트 21개 통과.

### 018-05 페이징 확인용 샘플 질문 300개

**바꾼 파일**
- `global/initData/BaseInitData.java`

**들어간 코드**
```java
return args -> {
    self.work();
    self.work2();
};

@Transactional
public void work2() {
    if (questionRepository.count() >= 100) return;
    for (int i = 1; i <= 300; i++) {
        Question q = new Question();
        q.setSubject("테스트 데이터입니다:[%03d]".formatted(i));
        q.setContent("내용무");
        questionRepository.save(q);
    }
}
```

**설명**
- 페이징은 데이터가 여러 페이지 분량이어야 화면에서 확인할 수 있다. 책 3-02는 테스트 코드를 한 번 실행해 300개를 넣는다. 강사식은 005-02의 `BaseInitData`처럼 dev 서버를 켤 때 넣는다.
- `"%03d".formatted(i)`는 숫자를 세 자리로 맞춘다(1 → `001`). 그래서 제목만 보고도 몇 번째 데이터인지 알 수 있다.
- `count() >= 100`이면 건너뛴다. `db_dev`는 파일 DB라서, 이 조건이 없으면 서버를 다시 켤 때마다 300개씩 계속 쌓인다.
- `work()`와 따로 만든 이유
  - `work()`는 "질문이 0개일 때만" 동작한다.
  - 이미 샘플 2개가 있어 `work()`는 건너뛴다. 하지만 300개는 새로 넣어야 했다.
  - 조건이 다른 작업은 메서드를 나눴다.
- `self.work2()`로 부르는 이유는 005-02와 같다. 프록시를 거쳐야 `@Transactional`이 적용된다.
- 300개를 한 트랜잭션에서 빠르게 저장해서, 일부 질문은 작성일시가 마이크로초까지 같다. 작성일시만으로 정렬하면 같은 값끼리의 순서는 DB가 정한다. 그래서 1페이지 맨 위가 `[300]`이 아니라 `[299]`였다.

- `/questions`: 맨 위가 최신 테스트 데이터이고, 페이지 버튼은 1~6이 보였다(현재 1페이지 + 뒤로 5개).

### 020-02 default_batch_fetch_size로 답변 조회 N+1 줄이기

**바꾼 파일**
- `application.yaml`

**들어간 코드**
```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

**설명**
- N+1 문제
  - 목록 쿼리 1번으로 질문 N개를 가져온다.
  - 그 뒤 질문마다 LAZY 관계(`answerList`)를 쓰면서 답변 쿼리가 N번 더 나간다.
  - 020-01의 답변 개수 표시 때문에 생겼다.
- `default_batch_fetch_size`는 Hibernate 설정이다.
  - LAZY 컬렉션 하나를 처음 쓸 때, 아직 읽지 않은 다른 질문들의 컬렉션까지 최대 100개를 모은다.
  - 그리고 `where question_id in (?, ?, ...)` 한 번으로 조회한다.
- 엔티티나 화면 코드를 고치지 않고 설정 한 줄로 쿼리 수가 줄어든다.
- 책에는 없고, 강사 강의에서 JPA를 쓸 때 기본으로 켜 두는 설정이다.
- 로그에 `?`가 100개 가까이 찍히는 이유: Hibernate가 쿼리 모양을 몇 가지 크기로 고정해 재사용하려고, 남는 자리를 채워 넣기 때문이다.

**검증 (dev 서버 로그로 SQL 수를 직접 셈)**

  - 변경 전 12개: 질문 목록 1 + 전체 개수 1 + 답변 10
  - 변경 후 3개: 질문 목록 1 + 전체 개수 1 + 답변 `in` 조회 1
- 화면 결과는 같고, 테스트 21개 통과.

### 021-01 의존성과 모든 요청 허용 설정

```java

```

**설명**
- 스프링 시큐리티는 요청이 컨트롤러에 닿기 전에 여러 보안 필터를 거치게 한다. 이 필터들의 규칙이 `SecurityFilterChain`이다.
- 시큐리티를 넣기만 하면 기본 규칙이 적용된다.
  - 모든 주소가 로그인 필요
  - 자동으로 만들어진 로그인 화면
  - 아직 회원 기능이 없으니 이 상태로는 아무 화면도 못 쓴다.
- `requestMatchers("/**").permitAll()`로 모든 주소를 허용했다. 강사식은 처음엔 전부 열고, 024처럼 필요한 곳만 막아 나간다.
- 테스트가 실패한 이유: CSRF 방어
  - 시큐리티는 CSRF 방어가 기본으로 켜져 있다.
  - 서버가 발급한 토큰이 없는 POST·PUT·DELETE 요청은 403으로 거부한다.
  - 다른 사이트가 사용자 브라우저를 이용해 몰래 요청을 보내는 공격을 막는 장치다.
- 테스트에서는 `spring-boot-starter-security-test`의 `csrf()`로 요청에 토큰을 붙인다.
- 반대로 토큰 없이 보내면 403이 나고 저장되지 않는지 확인하는 테스트도 추가했다.

**검증**
- 시큐리티를 넣은 직후 POST 테스트 4개가 403으로 실패했다.
- `.with(csrf())`를 붙이자 통과했다.
- 토큰 없는 POST는 403이고, 질문이 저장되지 않았다.
- 테스트 22개 통과.

### 021-02 H2 콘솔 CSRF 예외와 같은 사이트 프레임 허용

**바꾼 파일**
- `SecurityConfig.java`
- `QuestionControllerTests.java`

**들어간 코드**
```java
.csrf(csrf -> csrf
        .ignoringRequestMatchers("/h2-console/**"))
.headers(headers -> headers
        .frameOptions(frame -> frame.sameOrigin()));
```

**설명**
- 021-01 뒤 H2 콘솔이 두 가지 이유로 막혔다.
  1. **CSRF:** 콘솔 로그인은 POST다. 콘솔은 H2가 만든 화면이라 시큐리티의 CSRF 토큰을 보내지 못한다. 그래서 403이 난다.
  2. **프레임:** 콘솔 화면은 frameset으로 여러 프레임을 나눠 쓴다. 시큐리티는 기본으로 응답에 `X-Frame-Options: DENY`를 붙여 모든 프레임 표시를 막는다. 그래서 콘솔이 빈 화면이 된다.
- 해결
  - `ignoringRequestMatchers("/h2-console/**")`: 콘솔 주소만 CSRF 검사에서 뺀다. 우리 화면의 POST는 여전히 토큰을 검사한다.
  - `frameOptions(... sameOrigin())`: 같은 사이트(같은 주소·포트) 안의 프레임만 허용한다.
- `X-Frame-Options`는 원래 클릭재킹을 막는 헤더다. 클릭재킹은 다른 사이트가 우리 화면을 투명한 프레임으로 덮어 클릭을 훔치는 공격이다. `SAMEORIGIN`이면 다른 사이트의 프레임은 계속 막힌다.

**검증 (dev 서버를 다시 켜서 직접 요청)**
- 수정 전: `X-Frame-Options=DENY`, `POST /h2-console/login.do` → 403
- 수정 후: `X-Frame-Options=SAMEORIGIN`, 같은 요청 → 200, 응답이 frameset 화면(로그인 성공)
- MockMvc 테스트로 `/questions` 응답 헤더가 `SAMEORIGIN`인지 확인했다.
- 테스트 23개 통과.

### 021-03 th:action 폼의 CSRF 토큰 자동 삽입 확인

- 무작위 솔트를 섞기 때문에, 같은 비밀번호도 암호화할 때마다 결과가 다르다. 그래서 "같은 비밀번호를 쓰는 회원"도 드러나지 않는다.
- 비교는 `matches(입력값, 저장값)`로 한다. 저장값 안에 들어 있는 솔트로 입력값을 다시 계산해 맞춰 본다.
- 빈으로 등록해 두면 가입(022-04)과 로그인(023)이 같은 도구를 주입받아 쓴다.

**검증**
- `"1234"`를 두 번 암호화하면 둘 다 `$2a$`로 시작하고 서로 달랐다.
- `matches("1234", …)`는 true, `matches("4321", …)`는 false였다.
- 테스트 27개 통과.

```java
@PostMapping
public String join(@Valid MemberJoinForm memberJoinForm, BindingResult bindingResult) {
    if (bindingResult.hasErrors()) return "member_join";
    if (!memberJoinForm.password1().equals(memberJoinForm.password2())) {
```

### 023-01 시큐리티 회원 조회 MemberSecurityService

**만든 파일**
- `domain/member/member/service/MemberSecurityService.java`
- `MemberSecurityServiceTests.java`

**들어간 코드**
```java
@Service
public class MemberSecurityService implements UserDetailsService {
    @Override
    public UserDetails loadUserByUsername(String username) {
        Member member = memberRepository.findByUsername(username)
                .orElseThrow(() -> new UsernameNotFoundException("사용자를 찾을 수 없습니다."));
        List<GrantedAuthority> authorities = new ArrayList<>();
        authorities.add(new SimpleGrantedAuthority("ROLE_MEMBER"));
        if ("admin".equals(username)) authorities.add(new SimpleGrantedAuthority("ROLE_ADMIN"));
        return new User(member.getUsername(), member.getPassword(), authorities);
    }
}
```

**설명**
- 로그인 흐름에서 스프링 시큐리티는 "아이디 → 회원 정보"를 직접 알지 못한다. 그래서 `UserDetailsService`라는 약속(인터페이스)을 통해 물어본다.
- 이 인터페이스를 구현한 빈이 하나 있으면, 023-03의 폼 로그인이 자동으로 이 클래스를 쓴다.
- `loadUserByUsername`이 돌려주는 `UserDetails`(여기서는 시큐리티가 제공하는 `User`)에는 세 가지가 들어 있다.
  - 아이디
  - 암호화된 비밀번호
  - 권한 목록
- 비밀번호 비교는 여기서 하지 않는다. 시큐리티가 돌려받은 암호값과 사용자가 입력한 비밀번호를 022-03의 `PasswordEncoder.matches`로 비교한다.
- 권한 이름 앞의 `ROLE_`은 시큐리티 규칙이다. 나중에 `hasRole("ADMIN")`처럼 쓸 수 있다. `admin`에게 관리자 권한을 주는 규칙은 책과 같다.

**검증**
- `user1` 가입 후 조회: 아이디 일치, 비밀번호 `matches("1234")` true, 권한 `ROLE_MEMBER`
- `admin`: `ROLE_MEMBER`, `ROLE_ADMIN`
- 없는 아이디: `UsernameNotFoundException`
- 테스트 37개 통과.

### 025-01 _method 숨은 값으로 PUT·DELETE 받기

**바꾼·만든 파일**
- `application.yaml`
- `HiddenMethodFilterTests.java`: 새 파일

**들어간 코드**
```yaml
spring:
  mvc:
    hiddenmethod:
      filter:
        enabled: true
```

**설명**
- HTTP 메서드는 동작을 나타낸다(011-02 REST 규칙).
  - GET: 조회
  - POST: 생성
  - PUT: 수정
  - DELETE: 삭제
- 그런데 HTML `<form>`의 `method`는 GET, POST만 지원한다. 브라우저 폼으로는 PUT, DELETE를 직접 보낼 수 없다.
- `HiddenHttpMethodFilter`가 이 문제를 푼다.
  - 폼에 `<input type="hidden" name="_method" value="PUT">`을 넣고 POST로 보낸다.
  - 필터가 컨트롤러에 닿기 전에 이 요청을 PUT으로 바꾼다.
  - 그래서 컨트롤러는 `@PutMapping`, `@DeleteMapping`으로 받을 수 있다.
- 스프링 부트는 이 필터를 기본으로 꺼 둔다. 설정 한 줄로 켠다.
- 책은 수정을 `POST /question/modify/{id}`, 삭제를 `GET /question/delete/{id}`로 처리한다. GET 삭제는 링크 하나로 글이 지워질 수 있어 위험하다(023-04 로그아웃과 같은 이유).

**검증**
- 앱에 `HiddenHttpMethodFilter` 빈이 등록된 것을 테스트로 확인했다.
- 테스트 48개 통과.

### 025-02 QuestionService.modify 질문 수정

**바꾼 파일**
- `QuestionService.java`
- `QuestionServiceTests.java`

**들어간 코드**
```java
@Transactional
public void modify(Question question, String subject, String content) {
    question.setSubject(subject);
    question.setContent(content);
}
```

**설명**
- `save`를 부르지 않는데도 수정된다. JPA의 **변경 감지**(dirty checking) 덕분이다.
  - JPA는 읽어 온 엔티티를 기억해 둔다. 이 상태를 "영속 상태"라고 한다.
  - 트랜잭션이 끝날 때, 처음 상태와 달라진 필드를 찾아 `update` 쿼리를 보낸다.
- 컨트롤러가 넘긴 질문도 같은 영속성 컨텍스트에서 읽은 것이다. `open-in-view` 덕분에 요청이 끝날 때까지 열려 있다. 그래서 서비스 트랜잭션이 끝날 때 반영된다.
- 수정일시는 004-02의 `@LastModifiedDate`가 update 직전에 자동으로 바꾼다. 책은 `setModifyDate(LocalDateTime.now())`를 직접 부른다.

**검증**
- 질문을 저장하고 `flush`한 뒤 5ms 기다렸다. 바로 수정하면 두 시각이 같을 수 있기 때문이다.
- `modify` 후 다시 `flush`하고 새로 읽었다.
- 제목과 내용이 바뀌어 있었고, `modifyDate`가 `createDate`보다 늦었다.
- 테스트 49개 통과.

### 025-03 질문 수정 화면 GET /questions/{id}/edit

**바꾼·만든 파일**
- `QuestionController.java`
- `templates/question_modify.html`: 새 파일
- `QuestionControllerTests.java`

**들어간 코드**
```java
@PreAuthorize("isAuthenticated()")
@GetMapping("/{id}/edit")
public String showModify(@PathVariable Integer id, Model model, Principal principal) {
    Question question = questionService.getQuestion(id);
    checkAuthor(question, principal);
    model.addAttribute("questionForm", new QuestionForm(question.getSubject(), question.getContent()));
    model.addAttribute("questionId", id);
    return "question_modify";
}

private void checkAuthor(Question question, Principal principal) {
    if (question.getAuthor() == null || !question.getAuthor().getUsername().equals(principal.getName())) {
        throw new ResponseStatusException(HttpStatus.FORBIDDEN, "수정·삭제 권한이 없습니다.");
    }
}
```
```html
<form th:action="@{|/questions/${questionId}|}" th:object="${questionForm}" method="post">
    <input type="hidden" name="_method" value="put">
```

**설명**
- REST 규칙에서 "이 자원을 수정하는 입력 화면"은 `/questions/{id}/edit`이다. 실제 수정은 `PUT /questions/{id}`(025-04)다.
- 기존 값을 채우는 방법: 질문의 제목·내용으로 `QuestionForm` record를 만들어 모델에 담는다. `th:field`가 그 값을 `value`로 넣는다.
- 권한 확인 `checkAuthor`
  - 로그인 아이디와 질문 글쓴이 아이디가 다르면 `ResponseStatusException(FORBIDDEN)`을 던진다. 403 응답이 된다.
  - 글쓴이가 없는 옛 질문은 누구의 것도 아니라서 수정할 수 없다.
  - 025-04(수정 처리), 025-06(삭제)에서도 같은 메서드를 쓴다.
- `_method=put` 숨은 값: 025-01 필터가 이 폼의 POST를 PUT으로 바꾼다.
- 책은 등록 폼(`question_form`)을 수정에도 같이 쓴다. 여기서는 주소와 `_method`가 달라서 화면을 나눴다.

**검증**
